# CI secrets

The release pipeline (`build-webkit.yml`, `canary.yml`, `stable.yml`)
reads these secrets at the moments named below. None of them are
required for `ci.yml` to go green -- that workflow stays fork-friendly
and reads nothing but the tree.

The decisions behind these secrets live in **ADR-0109** (channels,
ad-hoc vs. Developer ID, Sparkle) and **ADR-0102** (the runner choice
that gates the rest). This document is the operator-facing list; the
ADRs are the reasoning.

## Runner

| Setting | Value | Why |
| --- | --- | --- |
| `runs-on` | `blacksmith-6vcpu-macos-15` | ADR-0109 names Blacksmith.sh. Blacksmith exposes its own labels; `blacksmith-6vcpu-macos-15` matches the `macos-15` floor ADR-0102 picks for `ci.yml`. See https://docs.blacksmith.sh/blacksmith-runners/overview. |
| `DEVELOPER_DIR` | `/Applications/Xcode_26.3.app/Contents/Developer` | Pinned against the same decision as `ci.yml`: a runner image update must not move the SDK under a build whose output is cached against a tag. Xcode 26+ is required because WebKit now compiles `.metal` shaders via the separately-downloaded Metal toolchain. **Verify the path exists on the Blacksmith image manifest** before the first run; if it does not, pin another 26.x and update both this file and `ci.yml`. |
| `timeout-minutes` (build-webkit) | `90` | Measured clean WebKit build is 35m34s; the slack is for the shallow clone and the runner warming up. |
| `timeout-minutes` (canary, stable) | `30` | The downstream job against a cached engine is ~10 min (ADR-0109). |

## Secrets

| Secret | When | Used by | Notes |
| --- | --- | --- | --- |
| `ZER0_SIGN_IDENTITY_CANARY` | When a Developer ID Application identity is enrolled for canary | `canary.yml` -> `scripts/sign.sh` | Optional today. Without it the canary build ships ad-hoc and only runs on the build machine -- useful for smoke-testing the pipeline, useless for distribution. |
| `ZER0_SIGN_IDENTITY_STABLE` | When a Developer ID Application identity is enrolled for stable | `stable.yml` -> `scripts/sign.sh` | **Required on stable.** `stable.yml` fails the job before the build if this is missing. |
| `ZER0_NOTARY_PROFILE` | When `xcrun notarytool store-credentials` has been run once on a runner keychain profile | `canary.yml` / `stable.yml` -> `scripts/notarize.sh` | Optional on canary, **required on stable**. The profile name is the only secret that has to live in CI; the `.p12` key, key id and team id are sealed inside the keychain profile. See `scripts/notarize.sh` header for the one-time `store-credentials` invocation. |
| `ZER0_SPARKLE_PRIVATE_KEY` | When the EdDSA appcast signing story is live | `canary.yml` / `stable.yml` -> `sign_update` | The private half of the pair generated by `sign_update -g` (see `docs/sparkle-setup.md`). Never print after generation; there is no recovery path. |
| `ZER0_SPARKLE_PUBLIC_KEY` | At bundle build time, when Sparkle is live | `apple/scripts/bundle.sh` (read via env at build time, not stored in CI) | Not strictly a CI secret -- it is the public half that ends up in `Info.plist` as `SUPublicEDKey`. Listed here because the project owns both halves of the pair; see `docs/sparkle-setup.md`. |

## Pending operational work

These are named in the workflows as `TODO(...)` markers and reproduced
here so they are not discovered late.

- **Blacksmith image manifest check.** The pinned `DEVELOPER_DIR` path
  is read off the GitHub-hosted image manifest (`ci.yml`). The
  Blacksmith macos-15 image may carry a different path; the first run
  of any of the three workflows will confirm or fail loudly at the
  `toolchain` step.
- **WebKit disk headroom.** `scripts/webkit/build.sh` requires 100 GB
  free via `require_free_gb`. The 6 vcpu Blacksmith macos runner needs
  to have that volume, or `build-webkit` refuses to start. If it does
  not, either move to a larger Blacksmith runner for that one job or
  point `ZER0_WEBKIT_DIR` at an attached volume.
- **`gh-pages` branch + feed host.** `scripts/publish-appcast.sh`
  (called from `canary.yml` and `stable.yml`) prepends a signed `<item>`
  to `appcast-{canary,stable}.xml` on the `gh-pages` branch and pushes.
  Two manual things have to happen once before the first publish lands a
  reachable entry:
  1. **Create the `gh-pages` branch** (empty orphan with the two seed
     appcasts at the root). The one-time commands are in
     `docs/sparkle-setup.md` § "One-time gh-pages setup"; the publish
     script refuses to create the branch itself, because two workflows
     inventing it at once is the race that loses history.
  2. **Point a host at the feed.** `Info.plist`'s `SUFeedURL` reads
     `https://download.thezer0.app/appcast-<channel>.xml` (ADR-0109);
     that domain has to map to `gh-pages` (GitHub Pages or a custom
     host) before Sparkle can read the feed. The **enclosure** URLs do
     not need that host -- they point at GitHub Releases
     (`github.com/<owner>/<repo>/releases/download/...`), which is live
     the moment the `create release` / `upload bundle to release` step
     runs. So `download.thezer0.app` carries the feed only; the binaries
     ride GitHub's CDN.
  The publish is gated on `ZER0_SPARKLE_PRIVATE_KEY`; until that secret
  exists the appcast step is skipped and the build stops at the uploaded
  artefact, which is the correct posture for a build with no signing
  story.
- **Real signing keys.** Nothing in this pipeline can ship to a
  stranger's Mac until `ZER0_SIGN_IDENTITY_STABLE` and
  `ZER0_NOTARY_PROFILE` exist. The pipeline is built so that the day
  they land is a secret-drop, not a code change.
- **`check.yml` was not added.** `ci.yml` already runs
  `./scripts/check.sh` on every pull request and every push to `main`
  and is the gate ADR-0030 names. Adding a second file would be a
  second gate, which ADR-0030 exists to prevent.
